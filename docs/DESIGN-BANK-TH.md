# การออกแบบและวิธีคิด — ทางเลือกสำรอง (ฉบับภาษาไทย)

ระบบจัดลำดับรายชื่อลูกค้าสำหรับขาย term deposit — โปรเจกต์ capstone วิชา ITCS355 **ทางเลือก B**

> **หมายเหตุ** เอกสารนี้เป็นคำแปลของ [`DESIGN-BANK.md`](DESIGN-BANK.md)
> ถ้าข้อความสองฉบับไม่ตรงกัน ให้ยึดฉบับภาษาอังกฤษ
> ศัพท์เทคนิคคงไว้เป็นภาษาอังกฤษโดยตั้งใจ เพราะโค้ดจริงใช้คำเหล่านั้น
> และ [`GLOSSARY.md`](GLOSSARY.md) อธิบายแต่ละคำไว้แล้ว

เขียนให้ลึกเท่ากับ [`DESIGN-TH.md`](DESIGN-TH.md) เพื่อให้เปรียบเทียบกันได้อย่างยุติธรรม

> **จุดที่ไม่เท่ากัน ต้องรู้ก่อนอ่าน** ตัวเลขทุกตัวในการออกแบบฝั่งคุณภาพอากาศ **วัดมาแล้วจริง ๆ**
> ข้อมูลดาวน์โหลดแล้ว วิเคราะห์แล้ว และเจอสถานีเสีย 5 แห่งจากการรันโค้ดจริง
> ส่วนตัวเลขทุกตัวในเอกสารนี้เป็นเพียง **การคาดการณ์** ยังไม่ได้ดาวน์โหลดอะไร
> ยังไม่ได้วิเคราะห์อะไร ยังไม่เจออะไร
> ข้อนี้ไม่ได้แปลว่าฝั่งไหนดีกว่าโดยตัวมันเอง แต่มันคือจุดเริ่มต้นจริง ๆ ของแต่ละทาง


> ### ข้อแก้ไข เพิ่มหลังจากดาวน์โหลดข้อมูลจริงแล้ว
>
> **เอกสารนี้เขียนขึ้นก่อนเปิดดูชุดข้อมูลจริง และข้อสรุปสำคัญข้อหนึ่งในนั้นผิด**
> ข้างล่างบอกว่าโปรเจกต์ธนาคารไม่มี drift ของจริง และทุกอย่างที่น่าสนใจต้องใส่เข้าไปเอง
> ข้อนั้นจริงสำหรับไฟล์ `bank-full.csv` แต่ **ไม่จริง** สำหรับ `bank-additional-full.csv`
> ซึ่งเป็นไฟล์ที่โปรเจกต์นี้ใช้จริง
>
> ไฟล์ที่เราใช้มีคอลัมน์เศรษฐกิจมหภาค 5 คอลัมน์ที่บันทึกไว้ ณ เวลาที่โทร
> และแคมเปญรันตั้งแต่พฤษภาคม 2008 ถึงพฤศจิกายน 2010 เรียงตามเวลา คือผ่านวิกฤตการเงินพอดี
> ค่า Euribor ลดจาก 4.86 เหลือ 0.80 อัตราการสมัครเพิ่มจาก 2.8% เป็น 45.9%
> และ 6 จาก 7 คอลัมน์ที่เฝ้าดูข้ามเกณฑ์ PSI **drift เป็นของจริง ไม่ต้องใส่เพิ่ม**
>
> ชุดข้อมูลยังมีกับดักข้อมูลรั่วเชิงเวลาของจริงด้วย การแบ่งแบบสุ่ม 50/50 ให้ 11.4% กับ 11.1%
> ซึ่งกลบการเปลี่ยนแปลงทั้งหมด ส่วนการแบ่งตามเวลาให้ 4.7% กับ 17.9%
>
> ย่อหน้าข้างล่างคงไว้ตามที่เขียนไว้เดิม เพราะการเปรียบเทียบนั้นคือสิ่งที่ใช้ตัดสินใจจริง ๆ
> การไปแก้ทิ้งจะเป็นการกลบว่าการตัดสินใจนั้นตั้งอยู่บนข้อมูลที่ผิดบางส่วน
> อ่านข้างล่างโดยรู้ว่ามีข้อแก้ไขนี้อยู่

## 1. ภาพรวมของระบบ

```
   ทำครั้งเดียว ด้วยมือ
       ดาวน์โหลด CSV หนึ่งไฟล์  ->  ตรวจ  ->  ทำ version
                     |
              data contract (ใน CI)
                     |
        features  ->  เทรน  ->  registry
                     |
   ทุกคืน โดยไม่มีคนกด
       อ่านรายชื่อวันนี้  ->  FRESHNESS GATE  ->  ทำนาย  ->  จัดลำดับ  ->  เผยแพร่
                     |
        metrics  ->  dashboard  ->  alert
                     |
              ตรวจจับ drift
```

## 2. ระบบนี้ทำอะไร

ธนาคารขาย term deposit ทางโทรศัพท์ สายส่วนใหญ่ไม่สำเร็จ และทุกสายกินเวลาพนักงาน
ทุกคืนระบบจะอ่านรายชื่อลูกค้าของวันพรุ่งนี้ ให้คะแนนแต่ละคน แล้วเผยแพร่รายชื่อ **ที่เรียงลำดับแล้ว**
คนที่มีโอกาสตอบตกลงมากที่สุดอยู่บนสุด พนักงานไล่โทรจากบนลงล่าง แทนที่จะโทรทั้งรายชื่อ

ธนาคารไม่ได้อยากได้ค่าความน่าจะเป็น ธนาคารอยากได้ลำดับ

## 3. แต่ละขั้นตอน

### ขั้นที่ 0 — เอาข้อมูลมา

**คืออะไร** ดาวน์โหลดชุดข้อมูล UCI Bank Marketing เป็น CSV หนึ่งไฟล์
45,211 แถว 16 คอลัมน์ และผลลัพธ์ใช่/ไม่ใช่ หนึ่งคอลัมน์ licence เป็น CC BY 4.0

**ทำไมถึงง่าย** เพราะมันเป็นไฟล์ มันไม่เปลี่ยน ไม่มี API ไม่ต้องใช้ key
ไม่มีลิมิตการเรียก ไม่ต้องไล่หน้า และไม่มี provider หลายเจ้าที่เงื่อนไขไม่เหมือนกัน

**ถ้าไม่ระวังจะพังยังไง** แทบไม่พัง ขั้นนี้คือขั้นที่ทางเลือกนี้ถูกกว่าชัดเจน
ประมาณห้านาที เทียบกับหนึ่งเย็นเต็ม ๆ

**ราคาที่ต้องจ่ายสำหรับความง่ายนั้น** ชุดข้อมูลนี้เป็นภาพนิ่งจากอดีตของธนาคารในโปรตุเกส
มันจะไม่มีวันเปลี่ยน แปลว่า **โปรเจกต์นี้ไม่มี drift ตามธรรมชาติ ไม่มีเหตุขัดข้องตามธรรมชาติ
และไม่มี sensor เสียตามธรรมชาติ** ทุกอย่างที่น่าสนใจต้องใส่เข้าไปเองด้วยมือ
รายละเอียดอยู่ที่ขั้นที่ 8

### ขั้นที่ 1 — ทำ version

**คืออะไร** ให้ DVC ดูแลไฟล์ CSV ส่วน git เก็บแค่ไฟล์บันทึก

**ทำไมต้องมี** เหตุผลเดียวกับอีกการออกแบบหนึ่ง คือ commit หนึ่งครั้งต้องชี้ไปที่ข้อมูลชุดเดียวเท่านั้น

**ถ้าไม่มีจะพังยังไง** พูดตามตรง พังน้อยกว่าฝั่งคุณภาพอากาศมาก
ไฟล์นิ่ง ๆ ที่ไม่เคยเปลี่ยน ย่อมเผลอเทรนผิดเวอร์ชันได้ยากกว่า
ขั้นนี้ยังจำเป็นเพื่อ R1 และยังเป็นวิธีที่ถูกต้อง แต่มันกันความเสี่ยงที่โปรเจกต์นี้แทบไม่มี

---

### ขั้นที่ 2 — Data contract

**คืออะไร** กฎที่เขียนเป็นฟังก์ชัน import ได้ ใช้ทั้งใน CI และกับงาน batch ทุกคืน
ได้แก่ คอลัมน์ที่ต้องมี ห้ามมีรหัสลูกค้าซ้ำ อายุต้องอยู่ในช่วงที่เป็นไปได้
ค่าประเภทต้องมาจากชุดค่าที่รู้จัก และคอลัมน์ `y` ต้องเป็น `yes` หรือ `no` เท่านั้น

**ทำไมต้องมี** ไฟล์จะไม่เปลี่ยนก็จริง แต่ **ระบบจริง** ที่มันจำลองอยู่นั้นเปลี่ยนแน่
contract คือสิ่งที่ทำให้แบบฝึกหัดนี้สมจริง และเป็นสิ่งที่จับความล้มเหลวในขั้นที่ 8 ได้

**ถ้าไม่มีจะพังยังไง** กฎที่แข็งแรงที่สุดตรงนี้คือกฎเรื่องค่าประเภท
ถ้าระบบต้นทางเริ่มเขียนคำว่า `unknown` ลงในคอลัมน์ `job` เป็นสัดส่วน 30% ของแถว
ทุกค่ายังเป็นข้อความที่ถูกต้อง ไม่มี error
แล้วโมเดลก็จะให้คะแนนลูกค้าหนึ่งในสามจากประเภทที่มันไม่เคยเรียนมาก่อน อย่างเงียบ ๆ
นี่คือความล้มเหลวแบบเดียวกับเรื่องเวลาไม่ตรงหัวชั่วโมงของอีกโปรเจกต์ และเงียบพอ ๆ กัน

**เรารู้ได้ยังไงว่าถูก** ใช้สองชั้นเหมือนกัน คือทำข้อมูลสะอาดให้พังทีละแบบ
แล้วยืนยันว่ากฎที่ตรงกันจับได้ จากนั้นทำ mutation check
คือปิดกฎหนึ่งข้อแล้วดูว่า test แดงตรงตามที่ควรแดงไหม

### ขั้นที่ 3 — คัดกรองคุณภาพ

**คืออะไร** ส่วนใหญ่ไม่จำเป็น

**ทำไม** เพราะไม่มี sensor ไม่มีสถานี ไม่มีอุปกรณ์ที่จะเสีย
ชุดข้อมูลวิจัยที่ถูกคัดมาแล้ว ย่อมถูกคนที่คัดมันเอาปัญหาคุณภาพออกไปแล้ว

**สิ่งที่โปรเจกต์นี้เสียไป** ในการออกแบบฝั่งคุณภาพอากาศ ขั้นที่ 3 คือจุดที่ระบบเจอ sensor ค้างของจริง
และผ่านมันไปเจอช่องโหว่จริงในการออกแบบ
แต่ที่นี่ไม่มีอะไรให้เจอ แปลว่างานน้อยลง และก็มีเรื่องให้พูดตอนปกป้องน้อยลงด้วย

---

### ขั้นที่ 4 — Features

**คืออะไร** อายุ อาชีพ สถานภาพสมรส การศึกษา ยอดเงินคงเหลือ สินเชื่อบ้านและสินเชื่อส่วนบุคคล
ช่องทางติดต่อ ประวัติแคมเปญ จำนวนวันตั้งแต่ติดต่อครั้งก่อน และผลลัพธ์ครั้งก่อน

**ทำไมต้องมี** เพราะมันคือสัญญาณ

**ถ้าไม่ระวังจะพังยังไง — โปรเจกต์นี้มีกับดักของตัวเอง** ชุดข้อมูลมีคอลัมน์ `duration`
คือความยาวของสายที่คุยกัน มันเป็นคอลัมน์ที่ทำนายได้ดีที่สุด และ **ใช้ไม่ได้**
เพราะตอนที่เราต้องทำนาย สายนั้นยังไม่ได้โทร
โมเดลที่เทรนโดยใส่คอลัมน์นี้จะได้คะแนนสวยมาก และไร้ค่าสิ้นเชิงตอนใช้งานจริง

นี่คือกับดักข้อมูลรั่วที่จริงจังพอ ๆ กับกับดัก lag ข้ามสถานีของอีกการออกแบบ
และมีข้อดีอย่างหนึ่งในแง่ตัวอย่างการสอน คือมันดังมาก
เอกสารของชุดข้อมูลเองก็เตือนเรื่องนี้ไว้ แปลว่าอาจารย์อาจถามว่าคุณสังเกตเห็นไหม

**เรารู้ได้ยังไงว่าถูก** เขียน test ที่ยืนยันว่า `duration` ไม่อยู่ในรายการ feature
พร้อมคอมเมนต์อธิบายเหตุผล test ตัวนี้ราคาถูก และเป็น test ที่มีค่าที่สุดของทางเลือกนี้

### ขั้นที่ 5 — เทรน โดยเทียบกับเส้นฐาน

**คืออะไร** ใช้ gradient-boosted tree ให้คะแนนลูกค้าแต่ละคน

**เส้นฐาน** มีสองอัน เพราะการจัดลำดับมีวิธีโง่ ๆ ที่นึกออกสองแบบ
คือโทรตามลำดับในไฟล์ และโทรโดยเรียงตามคอลัมน์เดียว เช่นผลลัพธ์ครั้งก่อน

**ถ้าไม่มีจะพังยังไง** สัดส่วนคำตอบที่นี่คือประมาณ 88% ตอบว่าไม่
โมเดลที่ทายว่า "ไม่" กับทุกคน จะแม่น 88% และไร้ประโยชน์โดยสมบูรณ์
ตัวเลขความแม่นยำที่พูดออกมาโดยไม่บอกบริบทนี้ จึงเป็นตัวเลขที่ชวนเข้าใจผิด
เพราะแบบนั้นตัววัดจึงควรเป็น lift ที่หัวรายชื่อ คือ *ในคน 500 คนแรกที่เราโทร มีกี่คนตอบตกลง*
ไม่ใช่ความแม่นยำ

**ยังไม่ได้วัด** ต่างจากเส้นฐานของฝั่งคุณภาพอากาศที่คำนวณไปแล้ว ตัวเลขพวกนี้ยังไม่มีอยู่จริง

### ขั้นที่ 7 — งาน batch ทุกคืน

**คืออะไร** Cloud Scheduler สั่ง container ให้ทำงานคืนละครั้ง
อ่านรายชื่อ ผ่าน gate ทำนาย จัดลำดับ เผยแพร่ ส่ง metrics

**ทำไมเลือก batch** ด้วยเหตุผลเดียวกับอีกโปรเจกต์ และหนักแน่นกว่าด้วย
พนักงานอ่านรายชื่อตอนเช้า ไม่มีใครนั่งรอคำทำนายที่จุดไหนเลย

**ต้นทุน** ตรงนี้คือจุดที่ทางเลือก B ชนะชัดเจน โดยใช้ราคาที่วัดไว้ใน Lab 5

| | คุณภาพอากาศ (รายชั่วโมง) | ธนาคาร (รายคืน) |
|---|--:|--:|
| จำนวนรอบต่อเดือน | 720 | 30 |
| เวลาประมวลผลที่คิดเงิน | 12.0 ชม. | 0.5 ชม. |
| **บาทต่อเดือน** | **46.32** | **1.93** |

ทั้งคู่ถือว่าน้อยมากเมื่อเทียบกับ endpoint ที่เปิดค้างไว้ราว 6,400 บาทต่อเดือน
ความต่างที่น่าสนใจจึงไม่ใช่เรื่องเงิน แต่เป็นเรื่องที่ว่า
เรื่องต้นทุนของฝั่งคุณภาพอากาศมีประเด็นให้ถกเถียง คือจ่ายเพิ่มเพื่อความสด
ส่วนฝั่งนี้ไม่มีประเด็นอะไรให้ถก

### ขั้นที่ 8 — ความล้มเหลวที่เราตั้งใจออกแบบ

**ความล้มเหลว** ไฟล์รายชื่อลูกค้าของคืนนั้นไม่มาส่ง ไฟล์ของเมื่อวานยังค้างอยู่ใน bucket
งานอ่านไฟล์นั้น ให้คะแนน แล้วเผยแพร่รายชื่อที่ดูปกติทุกอย่าง
จำนวนแถวเท่าเดิม การกระจายคะแนนเหมือนเดิม ไม่มี error ที่ไหน dashboard เขียวสนิท
เช้าวันรุ่งขึ้น พนักงานโทรหาคนกลุ่มเดิมกับที่โทรไปเมื่อวาน

**ทำไมถึงเป็นความล้มเหลวที่ดี** เพราะมันมีรูปร่างเดียวกับของฝั่งคุณภาพอากาศ
และรูปร่างนั้นคือสิ่งสำคัญ นั่นคือ *งานสำเร็จ แต่ผลลัพธ์ผิด* ไม่มีอะไรใน pipeline ปกติที่จะสังเกตเห็น

**ตัวควบคุม** อ่านเวลาที่ไฟล์ถูกแก้ไขล่าสุดก่อนทำนาย ไม่ใช่ดูแค่ว่าอ่านไฟล์สำเร็จไหม
ถ้าไฟล์เก่ากว่าข้อกำหนดความสด ให้ **ไม่เผยแพร่อะไรเลย แล้วส่ง alert**
รายชื่อที่หายไปคือปัญหาที่มีคนแก้ใน 10 นาที ส่วนรายชื่อที่ผิดแต่ดูน่าเชื่อ จะถูกเอาไปใช้ทั้งวัน

**จุดอ่อนที่ต้องพูดตรง ๆ** ความล้มเหลวนี้ต้อง **จัดฉากขึ้นมา**
ไม่มีอะไรในข้อมูลที่จะทำให้มันเกิดเองได้ เพราะ CSV เป็นภาพนิ่งจากหลายปีก่อน
คุณจะสาธิตมันด้วยการจงใจไม่ copy ไฟล์

เทียบกับฝั่งคุณภาพอากาศ ที่สถานี 2457250 นิ่งอยู่ที่ 1,680 µg/m³ ติดกัน 8 วันด้วยตัวมันเอง
และสถานี 2142801 หยุดส่งข้อมูลไปเลย โดยไม่มีใครไปจัดแจงอะไร
ความต่างระหว่าง "นี่คือความล้มเหลวที่ผมจัดฉากไว้" กับ "นี่คือความล้มเหลวที่ผมไปเจอมา"
คือความต่างที่การปกป้องงานถูกให้คะแนน

**อีกทางเลือกหนึ่งที่น่าสนใจกว่าสำหรับโปรเจกต์นี้** ชุดข้อมูลมีลักษณะที่รู้กันดีและน่าใช้ประโยชน์
คือคอลัมน์ `pdays` มีค่าเป็น −1 สำหรับลูกค้าที่ไม่เคยถูกติดต่อมาก่อน
นั่นคือค่าพิเศษที่ปลอมตัวมาเป็นตัวเลข
โมเดลที่ตีความ −1 ว่า "ติดต่อไปเมื่อ −1 วันก่อน" จะเรียนรู้อะไรที่ไร้สาระ และไม่มี error ใด ๆ
นี่คือกับดักของจริงที่มาจากตัวชุดข้อมูลเอง — แต่มันเป็นบั๊กเชิง **การสร้างโมเดล**
ไม่ใช่ความล้มเหลวเชิง **การปฏิบัติการ** และโจทย์ให้คะแนนที่ด้านปฏิบัติการ

### ขั้นที่ 9 — Monitoring และ drift

**คืออะไร** จำนวนแถวเข้า จำนวนแถวที่ให้คะแนน จำนวนแถวที่ถูกปฏิเสธ
การกระจายของคะแนน ระยะเวลาที่ใช้รัน และค่า PSI เทียบกับช่วงอ้างอิง

**ปัญหา** ไม่มี drift ของจริง เพราะชุดข้อมูลเป็นภาพนิ่งภาพเดียว
การกระจายจะไม่ขยับ เว้นแต่คุณไปขยับมันเอง

**สิ่งที่ต้องทำแทน** แบ่งไฟล์ตามลำดับแคมเปญ ใช้ส่วนแรกเป็นช่วงอ้างอิง แล้วใส่การเปลี่ยนแปลงเข้าไป
เช่นปรับน้ำหนักการกระจายของคอลัมน์ `job` เพื่อจำลองว่าธนาคารเปลี่ยนไปเจาะกลุ่มลูกค้าอีกแบบ
วิธีนี้ใช้ได้ อธิบายได้ และเห็นชัดว่าเป็นของสังเคราะห์

เทียบกัน ฝั่งคุณภาพอากาศมีค่ากลางเดือนมีนาคมอยู่ที่ 76.1 และเดือนมิถุนายนอยู่ที่ 5.6

### ถ้าเปลี่ยนไปทำธนาคาร ต้องจ่ายอะไรบ้าง

ฝั่งคุณภาพอากาศทำขั้นที่ 0 ถึง 3 เสร็จแล้ว คือดาวน์โหลดและทำ version ข้อมูล 155,109 แถว
มีรายงานวิเคราะห์ข้อมูล มี contract ที่มี test ผ่าน 23 ตัว
มีตัวคัดกรองที่เจอสถานีเสีย 5 แห่ง และมีการแก้การออกแบบที่มาจากการไปไล่ดูสถานีหนึ่ง

ส่วนฝั่งธนาคาร ขั้นที่ 0 และ 1 ใช้เวลาไม่ถึงหนึ่งชั่วโมง
ขั้นที่ 2 จะนานกว่าที่คิด เพราะกฎคนละชุด ถึงแม้โครงสร้างจะยกมาใช้ได้
ส่วนขั้นที่ 3 แทบจะหายไปเลย

**สรุปคร่าว ๆ คือ การเปลี่ยนใช้เวลาสองถึงสามชั่วโมง และเสียสิ่งที่ค้นพบไปหนึ่งเรื่อง**
ส่วน test, โครงสร้าง contract, การตั้ง DVC, CI, วิธีคิดต้นทุน และรูปร่างการออกแบบทั้งหมด
ยกไปใช้ได้โดยไม่ต้องแก้

### คำถามที่ควรถามจริง ๆ

ไม่ใช่ "อันไหนง่ายกว่า" เพราะทั้งคู่ทำไหวทั้งนั้น
คำถามคือ อันไหนที่คุณยังยืนอธิบายได้อยู่ ตอนท้ายการนำเสนอ 8 นาที
เมื่ออาจารย์ถามอะไรที่คุณไม่ได้เตรียมมา

กับฝั่งคุณภาพอากาศ คำตอบที่ซื่อสัตย์ของคำถามส่วนใหญ่คือตัวเลขที่คุณวัดมาเอง
กับฝั่งธนาคาร คำตอบมักจะเป็น "ตรงนั้นเราจำลองเอา"

แต่ในทางกลับกัน **การทำให้เสร็จ สำคัญกว่าการทำให้ประทับใจ**
โปรเจกต์ที่น่าเบื่อแต่ครบ ได้คะแนนทุกช่องในเกณฑ์
ส่วนโปรเจกต์ที่ทะเยอทะยานแต่ไม่เสร็จ ไม่ได้คะแนนช่องไหนเลยสักช่อง
เวลาที่มีอยู่จริงคือข้อจำกัดที่ควรใช้ตัดสินเรื่องนี้ ไม่ใช่ว่าการออกแบบอันไหนอ่านแล้วดูดีกว่า
