# การออกแบบและวิธีคิด (ฉบับภาษาไทย)

ระบบพยากรณ์ PM2.5 ล่วงหน้า 6 ชั่วโมง — โปรเจกต์ capstone วิชา ITCS355

> **หมายเหตุ** เอกสารนี้เป็นคำแปลของ [`DESIGN.md`](DESIGN.md) ถ้าข้อความสองฉบับไม่ตรงกัน
> ให้ยึดฉบับภาษาอังกฤษ ศัพท์เทคนิคคงไว้เป็นภาษาอังกฤษโดยตั้งใจ เพราะโค้ดจริงใช้คำเหล่านั้น
> และ [`GLOSSARY.md`](GLOSSARY.md) อธิบายแต่ละคำไว้แล้ว

เอกสารนี้มีไว้เพื่อให้ทุกส่วนของระบบ "พูดออกมาเป็นเหตุผลได้" แต่ละขั้นตอนตอบ 4 คำถาม
คือ **มันคืออะไร**, **ทำไมต้องมี**, **ถ้าไม่มีจะพังยังไง**, และ **เรารู้ได้ยังไงว่าเลือกถูก**
คำถามสุดท้ายคือคำถามที่ได้คะแนน เพราะโจทย์ให้คะแนนที่ระบบเชิงปฏิบัติการและการปกป้องมัน
ไม่ได้ให้ที่ตัวโมเดล

---

## 1. ภาพรวมของระบบ

```
   ทำครั้งเดียว ด้วยมือ
       เลือกสถานี + บันทึก licence  ->  ดาวน์โหลดประวัติ
                     |
              data contract (ใน CI)
                     |
             คัดกรองคุณภาพสถานี
                     |
        features  ->  เทรน  ->  registry
                     |
   ทุกชั่วโมง โดยไม่มีคนกด
       ดึงข้อมูลล่าสุด  ->  STALENESS GATE  ->  features  ->  ทำนาย  ->  เผยแพร่
                     |
        metrics  ->  dashboard  ->  alert
                     |
              ตรวจจับ drift
```

กล่องตัวใหญ่คือหัวใจของโปรเจกต์นี้ ส่วนที่เหลือคืองานประปาที่ทำให้ดี ส่วน gate คือส่วนที่มีเหตุผลรองรับจริง ๆ

---

## 2. หลักการที่ใช้ตัดสินใจทุกเรื่องในเอกสารนี้

ไม่ใช่คำขวัญ แต่ละข้อเคยเปลี่ยนการตัดสินใจจริงในโปรเจกต์นี้มาแล้ว

**P1 — วัดก่อน แล้วค่อยเลือก**
ตัวเลขที่ไม่มีใครวัด คือความเห็นที่ใส่ชุดเป็นตัวเลข ตอนแรกเราตั้ง staleness threshold ไว้ที่
3 ชั่วโมง เพราะ "รู้สึกว่าปลอดภัยดี" พอวัดการกระจายของช่องว่างจริง ๆ คำตอบคือ 2 ชั่วโมง
พร้อมตัวเลขอัตราเตือนผิดที่ยืนยันได้

**P2 — คำตอบที่ผิด แย่กว่าไม่มีคำตอบ**
ระบบที่ปฏิเสธจะตอบ สร้างปัญหาที่มองเห็น แล้วมีคนแก้ใน 10 นาที
ระบบที่ตอบผิด สร้างปัญหาที่มองไม่เห็น แล้วมีคนเอาไปใช้ตัดสินใจ
ทุก gate ในระบบนี้เลือกที่จะปฏิเสธ

**P3 — test ที่ไม่เคยพัง คือ test ที่ยังไม่รู้ว่าใช้ได้จริงไหม**
เราพิสูจน์กฎทุกข้อด้วยการทำข้อมูลให้พังโดยตั้งใจ แล้วดูว่ากฎนั้นจับได้ไหม
และยังทำ mutation check ด้วย คือปิดกฎหนึ่งข้อ ดูว่า test ที่คุมกฎนั้นแดงไหม แล้วเปิดคืน

**P4 — นิยามเดียว ใช้สองที่**
อะไรที่บังคับใช้ทั้งใน CI และตอน serve เราเขียนครั้งเดียวแล้ว import ไปใช้สองที่
ถ้าเขียนสองชุด มันจะค่อย ๆ ต่างกัน และมักต่างไปในทางที่ชุดฝั่ง serve อ่อนกว่าชุดที่คนตรวจ

**P5 — ความแม่นยำไม่ได้คะแนนที่นี่**
โจทย์เขียนไว้ตรง ๆ แรงงานจึงทุ่มไปที่ระบบเชิงปฏิบัติการ
โมเดลใช้แบบที่ถูกที่สุดที่ชนะ persistence ได้พอ

## 3. แต่ละขั้นตอน

### ขั้นที่ 0 — เลือกสถานีให้ตายตัว และบันทึก licence

**คืออะไร** `scripts/find_stations.py` ค้นหาสถานี PM2.5 ในไทยจาก OpenAQ เก็บเป็นรายชื่อตายตัว
แล้วเขียนลง `data/stations.json` พร้อม provider และ licence ของแต่ละสถานี

**ทำไมต้องมี** คำว่า "สถานีทั้งหมดในไทย" ให้ผลไม่เหมือนกันทุกเดือน
ชุดข้อมูลที่นิยามด้วยคำค้น สร้างใหม่ให้เหมือนเดิมไม่ได้ แต่ชุดที่นิยามด้วยรายชื่อ ทำได้

**ถ้าไม่มีจะพังยังไง** พอเทรนใหม่ในเดือนพฤศจิกายนด้วย "สถานีทั้งหมดในไทย"
มันจะเทรนกับประชากรคนละชุดกับโมเดลเดือนกันยายน โดยเงียบ ๆ
การเปรียบเทียบสองโมเดลจะไม่มีความหมาย และไม่มีอะไรในระบบบอกว่ามีอะไรเปลี่ยน

**เรารู้ได้ยังไงว่าถูก** เพราะมันช่วยชีวิตไปแล้วจริง ๆ รันรอบแรกได้สถานีมา 40 แห่ง
ซึ่งปรากฏว่า **ไม่มี licence เลยสักแห่ง** ทั้งหมดเป็นสถานีของราชการ (Air4Thai)
พอไล่ดูทั้ง 618 สถานีในไทยได้ผลแบบนี้

| Provider | จำนวนสถานี | Licence |
|---|--:|---|
| AirGradient | 346 | **CC BY 4.0** |
| Air4Thai | 263 | ไม่ระบุ |
| Clarity | 3 | CC0 1.0 |
| AirNow | 1 | US Public Domain |

ตอนนี้สคริปต์ **ปฏิเสธสถานีที่ไม่ระบุ licence เป็นค่าตั้งต้น**
ถ้าจะเอาเข้ามาต้องใส่ flag ชัดเจน แล้ว proposal ต้องอธิบายว่าอ้างอิงอะไรแทน licence

**สิ่งที่ต้องแลก** AirGradient เป็น sensor ราคาถูกของชุมชน ไม่ใช่เครื่องมาตรฐานของราชการ
ค่าที่อ่านได้จึงมี noise มากกว่า แต่ความแม่นยำไม่ได้คะแนน (P5)
และ sensor ราคาถูกเสียบ่อยกว่า ซึ่งทำให้การสาธิตความล้มเหลวของเรา **สมจริงขึ้น ไม่ใช่แย่ลง**

### ขั้นที่ 1 — ดาวน์โหลดประวัติครั้งเดียว แล้วทำ version

**คืออะไร** `scripts/download_measurements.py` ดึงข้อมูลรายชั่วโมงย้อนหลัง 6 เดือนของแต่ละสถานี
มาเก็บใน `data/raw/` สถานีละหนึ่งไฟล์ CSV แล้วให้ DVC ดูแลโฟลเดอร์นั้น
ส่วน git เก็บแค่ไฟล์บันทึกสั้น ๆ 5 บรรทัด

**ทำไมต้องมี** การเทรนต้องไม่พึ่ง API สด ๆ
เพราะ API ช้า มีลิมิต ต้องใช้ key และให้ข้อมูลไม่เหมือนเดิมทุกชั่วโมง

**ถ้าไม่มีจะพังยังไง** การเทรนจะทำซ้ำไม่ได้ตั้งแต่ต้น
รันห่างกันหนึ่งชั่วโมงก็เห็นข้อมูลคนละชุดแล้ว อาจารย์สร้างผลลัพธ์ของคุณขึ้นมาใหม่ไม่ได้ และคุณเองก็ไม่ได้

**เรารู้ได้ยังไงว่าถูก** เพราะทดสอบจริง ไม่ได้เดา
เรา clone repo ใหม่ลงโฟลเดอร์เปล่า สั่ง `dvc pull` แล้วยืนยันว่าไฟล์ทั้ง 39 ไฟล์
กลับมา **เหมือนเดิมทุก byte** (ค่า md5 ของชุดไฟล์ตรงกัน)
การทดสอบวนกลับแบบนี้คือสิ่งที่ `dvc pull` อ้างว่าทำได้ และปกติไม่มีใครตรวจ

**รายละเอียดที่สำคัญมาก** ชั่วโมงที่ไม่มีข้อมูลจะถูก **ข้ามไป ไม่เติมศูนย์**
เพราะศูนย์แปลว่า "อากาศสะอาดสนิท" ไม่ได้แปลว่า "เราไม่มีค่า"
ซึ่งเป็นความสับสนแบบเดียวกับที่โปรเจกต์ทั้งโปรเจกต์นี้สร้างขึ้นมาเพื่อแก้
ถ้าพลาดตรงนี้ตั้งแต่ตอนดาวน์โหลด มันจะทำลายสิ่งที่เรากำลังจะถูกให้คะแนนอย่างเงียบ ๆ

### ขั้นที่ 2 — Data contract

**คืออะไร** `src/contract.py` เก็บกฎไว้เป็นฟังก์ชันที่คืนค่ารายการสิ่งที่ผิด
ใช้ตอน CI กับชุดข้อมูลทั้งก้อน และใช้ตอนงานรายชั่วโมงกับข้อมูลแต่ละรอบ

**ทำไมต้องมี** ข้อมูลต้นทางไม่ใช่ของเรา
เขาเปลี่ยนชื่อคอลัมน์ได้ เปลี่ยนหน่วยได้ เปลี่ยนวิธีรวมข้อมูลได้
หรือเริ่มส่งสถานีจากประเทศอื่นมาก็ได้ และไม่มีอันไหนที่จะขึ้น error ให้เห็นเอง

**ถ้าไม่มีจะพังยังไง** อันที่เงียบที่สุดคือเรื่องการรวมข้อมูล
ถ้า endpoint เลิกส่งค่าที่ตรงหัวชั่วโมง ค่าทุกค่ายังดูปกติ ไม่มี error
แต่ lag feature จะเริ่มเปรียบเทียบค่าที่ห่างกันไม่เท่ากันโดยเงียบ ๆ
และไม่มี test ไหนหลังจากนั้นจับได้ เพราะตัวเลขยังดูเหมือน PM2.5 อยู่ดี

**เรารู้ได้ยังไงว่าถูก** มีสองชั้น

1. `tests/test_contract_catches_breakage.py` ทำข้อมูลสะอาดให้พังทีละแบบ
   แล้วยืนยันว่ากฎที่เกี่ยวข้องจับได้ ได้แก่ คอลัมน์หาย ชั่วโมงซ้ำ ค่าว่าง ค่าติดลบ
   ค่าเกินเพดาน เวลาไม่ตรงหัวชั่วโมง หน่วยเปลี่ยน พิกัดนอกประเทศ สถานีที่ไม่ได้เลือกไว้
   ประวัติสั้นเกินไป และแบบที่พังหลายอย่างพร้อมกัน
2. **mutation check** คือปิดกฎ "ค่าติดลบ" ทิ้ง แล้วพบว่ามี test แดงพอดี 2 ตัว
   พอเปิดคืนก็เขียวทั้งคู่ กฎที่ปิดทิ้งได้โดยไม่มี test ไหนรู้สึก ไม่ใช่กฎ

**รายละเอียดการออกแบบ** `validate()` คืน **ทุกข้อผิด** ไม่ใช่หยุดที่ข้อแรก
เพราะข้อมูลที่พังสามแบบ ควรใช้เวลาวินิจฉัยหนึ่งบ่าย ไม่ใช่สามรอบ build

**สิ่งที่จงใจไม่ใส่ใน contract** คือค่าศูนย์เป๊ะ ๆ และค่าพุ่งสูงผิดปกติ
เพราะ 25 จาก 39 สถานีมีค่าศูนย์อย่างน้อยหนึ่งครั้ง และมีสถานีหนึ่งรายงานศูนย์ถึง 17.8%
เครือข่าย sensor จริงย่อมมีตัวเสียเสมอ และ contract ที่พังกับสภาพปกติของโลก จะถูกปิดทิ้ง
เรื่องพวกนี้ไปอยู่ในขั้นที่ 3 แทน

### ขั้นที่ 3 — คัดกรองคุณภาพสถานี

**คืออะไร** ตัวคัดกรองรายสถานี ที่ตัดสินว่าสถานีไหนเอาไปเทรนได้
แล้วเขียนรายชื่อที่ตัดออกพร้อมเหตุผลลงไฟล์

**ทำไมต้องมี** contract พังแปลว่า **ข้อมูลต้นทางเสีย**
คุณภาพไม่ผ่านแปลว่า **sensor ตัวนี้เสีย** สองอย่างนี้ต้องตอบสนองต่างกัน
อย่างแรกคือหยุดทุกอย่าง อย่างหลังคือตัดสถานีนั้นทิ้งแล้วทำต่อ

**ถ้าไม่มีจะพังยังไง** ถ้าเทรนรวมสถานี 2142493 ที่รายงานศูนย์ถึง 17.8%
โมเดลจะเรียนรู้ว่าตรงนั้นอากาศสะอาดบ่อย
หรือพลาดอีกทางคือ ทำให้ build ทั้งอันพังเพราะ sensor ตัวเดียวเสีย
แปลว่าไม่มีใครส่งงานได้เลยจนกว่าคนอื่นจะไปซ่อมฮาร์ดแวร์ที่ไม่ใช่ของเรา

**เรารู้ได้ยังไงว่าถูก** เกณฑ์ทั้งสองอยู่ในช่องว่างกว้าง ๆ ระหว่างสถานีที่เสียกับสถานีปกติ
ผลลัพธ์จึงไม่ขึ้นกับว่าเราเลือกตัวเลขไหนพอดี

*อัตราค่าศูนย์ เกณฑ์ 5%* สามสถานีที่แย่ที่สุดอยู่ที่ 17.79%, 8.05% และ 7.75%
ส่วนอันดับสี่อยู่ที่ 1.48% ดังนั้นเกณฑ์ตรงไหนก็ได้ระหว่าง 1.5% ถึง 7.7% จะได้สามสถานีเดิม

*ช่วงค่านิ่ง เกณฑ์ 24 ชั่วโมง* ครึ่งหนึ่งของสถานีไม่เคยนิ่งเกิน 5 ชั่วโมง และ 95% ไม่เกิน 15 ชั่วโมง
สถานีที่เสียนิ่งอยู่ 52 ชั่วโมง ส่วนอันดับถัดมาคือ 21 ชั่วโมง

test ตรวจทั้งสองทิศทาง คือจับของเสียได้ **และ** ไม่ตัดสถานีปกติที่มีศูนย์ไม่กี่ครั้งหรือนิ่งไม่กี่ชั่วโมง
ตัวคัดกรองที่ตัดทุกอย่างทิ้ง ไร้ประโยชน์พอ ๆ กับตัวที่ไม่ตัดอะไรเลย และเขียนพลาดแบบนั้นง่ายกว่าด้วย

**ผลลัพธ์ — ตัดออก 5 จาก 40 สถานี เหลือใช้ได้ 35**

| สถานี | เหตุผล | หลักฐาน |
|---|---|---|
| 2142493 | อัตราค่าศูนย์ผิดปกติ | ค่าศูนย์ 17.8% |
| 1236050 | อัตราค่าศูนย์ผิดปกติ | 8.1% |
| 2165656 | อัตราค่าศูนย์ผิดปกติ | 7.7% |
| 2457250 | **sensor ค้าง** | ค่าเดิมนิ่งติดกัน 52 ชั่วโมง |
| 2142801 | ไม่มีข้อมูล | เลือกไว้แต่ไม่ส่งอะไรมาเลย |

**รายชื่อที่ตัดออกอยู่ในไฟล์ ไม่ได้ฝังในสคริปต์เทรน** คนตรวจเห็นได้โดยไม่ต้องอ่านโค้ด
จำนวนที่ถูกตัดกลายเป็น metric ทำให้เห็นว่าเครือข่ายกำลังเสื่อมลงเงียบ ๆ หรือไม่
และถ้าสถานีไหนกลับมาดี ก็แค่รันตัวคัดกรองใหม่ ไม่ต้องหวังให้ใครจำได้ว่ามีรายชื่อฝังอยู่ตรงไหน

### ขั้นที่ 4 — Features (ยังไม่ได้ทำ)

**คืออะไร** ค่า PM2.5 ย้อนหลัง (1, 2, 3, 6, 12, 24 ชั่วโมง), ค่าเฉลี่ยเคลื่อนที่,
ชั่วโมงของวัน, วันของสัปดาห์, และรหัสสถานี

**ทำไมต้องมี** เพราะโมเดลทำนาย 6 ชั่วโมงข้างหน้าจากอดีตที่เพิ่งผ่านมา ค่าย้อนหลังพวกนี้คือสัญญาณ

**ถ้าไม่มีจะพังยังไง — และนี่คือกับดัก** ค่าย้อนหลังต้องสร้าง **แยกรายสถานี และเรียงตามเวลา**
ถ้าเลื่อนทั้งตารางรวดเดียว ประวัติของสถานี A จะรั่วไปเป็น feature ของสถานี B
โมเดลจะทำคะแนนดีมากตอน validate แล้วพังตอนใช้จริง
เพราะมันเรียนจากข้อมูลที่ตอนใช้งานจริงมันจะไม่มีวันมี

**เราจะรู้ได้ยังไงว่าถูก** ป้องกันสองชั้น
ชั้นแรกคือ test ที่สร้าง feature ให้สองสถานีที่มีค่าต่างกันอย่างจงใจ
แล้วยืนยันว่าไม่มีค่าของสถานีหนึ่งโผล่ไปอยู่ในอีกสถานี
ชั้นที่สองคือแบ่งข้อมูลตามเวลา เทรนด้วยช่วงก่อน ตรวจด้วยช่วงหลัง
**ห้ามแบ่งแบบสุ่ม** เพราะการสุ่มทำให้โมเดลเห็นอนาคต

### ขั้นที่ 6 — Registry และ lineage

**คืออะไร** เวลาลงทะเบียนโมเดล ต้องแนบข้อมูลที่ตอบคำถามว่า "โมเดลนี้มาจากไหน"
ได้แก่ git commit, image digest, เวอร์ชันข้อมูล (ค่า hash ของ DVC), รหัสงานที่เทรน, seed และคะแนน

**ทำไมต้องมี** อีกสามเดือน คำถามเดียวที่สำคัญเกี่ยวกับโมเดลที่ใช้งานอยู่
คือมันมาจากโค้ดชุดไหนและข้อมูลชุดไหน

**ถ้าไม่มีจะพังยังไง — เจอมาแล้วใน Lab 2** ค่า `git_commit` ถูกบันทึกเป็นคำว่า `unknown`
เพราะใน container ไม่มีโฟลเดอร์ `.git`
ช่องที่มีหน้าที่ตอบคำถามนี้โดยตรง กลับตอบว่าไม่รู้ **และการลงทะเบียนก็ยังสำเร็จ**
ช่อง lineage ที่ปล่อยให้ว่างได้โดยไม่พัง จะว่างในวันที่เราต้องการมันพอดี

### ขั้นที่ 7 — งาน batch รายชั่วโมง

**คืออะไร** Cloud Scheduler สั่ง container ให้ทำงาน
ดึงข้อมูลล่าสุด → ผ่าน gate → สร้าง features → ทำนาย → เผยแพร่ → ส่ง metrics

**ทำไมเลือก batch ไม่เลือก endpoint** พยากรณ์ที่อัปเดตทุกชั่วโมง
ไม่มีทางมีประโยชน์เกินกว่ารายชั่วโมงอยู่แล้ว ไม่ว่าจะ serve แบบไหน
ตัวเลขจากที่เราวัดเองใน Lab 3 และ Lab 5

| ทางเลือก | บาท/เดือน |
|---|--:|
| endpoint เปิดค้างไว้ | ~6,400 |
| batch ทุก 30 นาที | 92.64 |
| **batch ทุกชั่วโมง (ที่เลือก)** | **46.32** |
| batch ทุก 3 ชั่วโมง | 15.44 |
| batch วันละครั้ง | 1.93 |

**ทำไมไม่เลือกแถวที่ถูกที่สุด** ทุก 3 ชั่วโมงประหยัดได้เดือนละ 31 บาท
แต่ทำให้พยากรณ์อาจเก่าไปแล้ว 2 ชั่วโมงตอนที่คนเปิดอ่าน ซึ่งผิดข้อกำหนดเรื่องความสดของข้อมูล
ส่วนวันละครั้งไม่มีประโยชน์เลยกับปัญหาที่ทั้งหมดอยู่ที่การเปลี่ยนแปลงภายในวัน

**ข้อสังเกตที่ต้องพูดตรง ๆ** ค่าใช้จ่ายตรงนี้มาจาก **จำนวนรอบที่รัน ไม่ใช่ปริมาณงาน**
แต่ละรอบใช้เวลาประมาณหนึ่งนาที พอรัน 720 รอบต่อเดือน เราจ่ายค่า overhead ต่อรอบเป็นหลัก
นั่นคือราคาของความสด และมันมองไม่เห็นจนกว่าจะนั่งนับจำนวนรอบ

### ขั้นที่ 8 — Staleness gate (ความล้มเหลวที่เราตั้งใจออกแบบ)

**ความล้มเหลว** สถานีหนึ่งหยุดส่งข้อมูล
ตัวดึงข้อมูลได้ HTTP 200 ปกติ จำนวนแถวเท่าเดิมเพราะค่าเก่ายังอยู่
การกระจายของคะแนนดูปกติ โมเดลพยากรณ์ออกมาอย่างมั่นใจ
แผนที่แสดงว่าอากาศสะอาดในจุดที่จริง ๆ แล้วไม่มีข้อมูลเลย
และมันแสดงแบบนั้นพอดีในช่วงที่มีคนกำลังเช็กว่าออกไปข้างนอกได้ไหม

**ทำไมเลือกความล้มเหลวแบบนี้** เพราะมันมองไม่เห็นด้วยการตรวจทุกแบบที่ pipeline ปกติมี
ไม่มี error ไม่มีอะไรดูแปลก และผลลัพธ์ถูกเอาไปใช้จริง

**ตัวควบคุม** ก่อนทำนาย ให้อ่าน **เวลาของค่าวัดเอง** ไม่ใช่ดูสถานะ HTTP
สถานีที่ค่าล่าสุดเก่ากว่า **2 ชั่วโมง** จะถูกตัดออกและแสดงว่า "ไม่มีข้อมูล"
พร้อมส่งจำนวนสถานีที่ถูกตัดเป็น metric และตั้ง alert ไว้

**ทำไมถึงเป็น 2 ชั่วโมง พร้อมตัวเลขรองรับ** จากข้อมูลย้อนหลัง 6 เดือน

- 99.5% ของค่าที่อ่านติดกัน ห่างกันหนึ่งชั่วโมงพอดี
- ช่องว่างเกิน 2 ชั่วโมง เกิดขึ้น 0.30% ของช่วงทั้งหมด
- ช่องว่างเกิน 3 ชั่วโมง เกิดขึ้น 0.23%

ดังนั้น 2 ชั่วโมงจับเหตุได้เร็วขึ้นหนึ่งชั่วโมง โดยแลกกับการเตือนผิดเพิ่มแค่ 0.07 จุดเปอร์เซ็นต์
gate ที่เด้งบ่อยตอนระบบปกติ จะถูกปิดทิ้ง และ gate ที่ถูกปิดทิ้งแย่กว่าไม่มี gate
เพราะมันยังอ้างอยู่ว่ามีคนเฝ้าดูอยู่

**เราไม่ต้องแกล้งสร้างเหตุการณ์** สถานี 2457250 มีอยู่จริง และเสียทั้งสองแบบ

### ช่องโหว่ที่การออกแบบเดิมมี

พอไปไล่ดูสถานีนี้จริง ๆ การออกแบบก็เปลี่ยน มันไม่ได้แค่ค่าพุ่งชั่วคราว
แต่มันนิ่งอยู่ที่ค่ากลาง **1,680 µg/m³ ติดกัน 8 วัน**
ขณะที่สถานีอื่นทั้งหมดมีค่า p95 ไม่ถึง 60
นั่นคือ sensor ที่ค้างอยู่ใกล้ค่าสูงสุดของมัน และประเด็นสำคัญคือ

**sensor ที่ค้าง ผ่าน staleness gate ได้สบาย** เพราะมันส่งเวลาใหม่ตลอดเวลา
ข้อมูลสดมาก และผิดสนิท

การออกแบบเดิมตรวจแค่ว่าข้อมูล **ใหม่หรือไม่** ไม่เคยตรวจว่า **เป็นไปได้หรือไม่**
ความล้มเหลวแบบนี้จึงเดินผ่านไปได้เลย เครือข่ายจึงมีความล้มเหลวสองแบบ ที่ต้องมีตัวคุมสองตัว

| ความล้มเหลว | หน้าตาเป็นยังไง | จับด้วยอะไร |
|---|---|---|
| สถานีเงียบหายไป | ไม่มีค่าใหม่เข้ามา | **staleness gate** — เวลาเก่ากว่า 2 ชม. |
| สถานีค้าง | ค่าใหม่มาเรื่อย ๆ แต่ค่าเท่าเดิม | **ตัวตรวจค่านิ่ง** — ค่าเดิมนานกว่า 24 ชม. |

ตัวคุมทั้งสองต้องอยู่ในงานรายชั่วโมงด้วย ไม่ใช่อยู่แค่ตอนคัดกรองก่อนเทรน
เพราะความล้มเหลวทั้งสองแบบเกิดตอนใช้งานจริง
และการสาธิตจะแข็งแรงขึ้นด้วย เพราะเราโชว์ได้ทั้งสถานีที่หายไป และสถานีที่โกหก
แล้วชี้ให้เห็นว่าวิธีป้องกันแบบที่นึกออกง่าย ๆ จับได้แค่อันเดียว

สังเกตด้วยว่าอะไรที่ **จับไม่ได้** ค่า 1,680 ยังต่ำกว่าเพดานทางกายภาพที่ contract ตั้งไว้ที่ 2,000
การตรวจช่วงค่าจึงปล่อยผ่าน มันจับได้ด้วยการเทียบสถานีกับตัวมันเองข้ามเวลา หรือเทียบกับสถานีข้างเคียงเท่านั้น

### ขั้นที่ 9 — Monitoring และ drift ที่เป็นของจริง

**คืออะไร** metric ต่อรอบ ได้แก่ จำนวนแถวเข้า จำนวนสถานีที่ถูกตัด การกระจายของค่าพยากรณ์
ระยะเวลาที่ใช้รัน และค่า PSI ระหว่างช่วงอ้างอิงกับช่วงปัจจุบัน

**ทำไมต้องมี** เพราะเฉลยมาถึงช้ากว่า 6 ชั่วโมง เราจึงเช็กคุณภาพตอน serve ไม่ได้
สถิติฝั่งข้อมูลเข้าเป็นสัญญาณเดียวที่ได้ภายในวันเดียวกัน

**สิ่งที่เราได้มาฟรี ๆ** ฤดูเผาคือการเปลี่ยนการกระจายของจริง

| เดือน | ค่ากลาง PM2.5 |
|---|--:|
| มีนาคม | 76.1 |
| เมษายน | 72.0 |
| พฤษภาคม | 12.5 |
| มิถุนายน | 5.6 |

มีนาคมสูงกว่ามิถุนายน 13 เท่า ทีมอื่นส่วนใหญ่ต้องแกล้งสร้าง drift ขึ้นมาเอง
แต่ของเรามีอยู่ในข้อมูลแล้ว และ 18.3% ของค่าทั้งหมดเกินมาตรฐาน 24 ชั่วโมงของไทยที่ 37.5 µg/m³

**ถ้าไม่มีจะพังยังไง — วัดมาแล้วใน Lab 4** PSI เรียงลำดับตาม "ข้อมูลขยับไปไกลแค่ไหน"
ไม่ใช่ "โมเดลเดือดร้อนแค่ไหน" การขยับที่ได้ PSI 0.383 ทำให้คะแนนตก 0.0100
ส่วนอีกกรณีที่ได้ PSI แค่ 0.2627 กลับทำให้ตกถึง 0.0167
dashboard จึงต้องแสดงทั้งสองอย่าง ไม่งั้นมันจะจัดลำดับความสำคัญของเหตุการณ์ผิด

## 4. วิธีคิด: เราตัดสินใจกันยังไง

**ตัดสินใจด้วยตัวเลขที่วัดได้ แล้วเขียนตัวเลขนั้นไว้ข้าง ๆ การตัดสินใจ**
ทุก threshold ในเอกสารนี้มีตัวเลขที่ทำให้เลือกแบบนั้นกำกับอยู่
"2 ชั่วโมง เพราะช่วงปกติเกินค่านี้แค่ 0.30%" ตอบคำถามได้
ส่วน "3 ชั่วโมง เพราะรู้สึกว่าปลอดภัย" ตอบไม่ได้

**เขียน test ก่อนเขียนสิ่งที่มันตรวจ เพราะ test คือข้อกำหนด**
contract ถูกเขียนก่อน feature ที่ต้องพึ่งมัน แล้วมันก็จับได้ว่า
รายชื่อสถานีชุดแรกของเราเองไม่มี licence ตั้งแต่ก่อนจะมี feature สักตัว

**ทำให้พังโดยตั้งใจ แล้วเก็บตัวที่ทำให้พังไว้**
กฎทุกข้อมี test ที่ป้อนความล้มเหลวแบบที่มันมีไว้ดักโดยเฉพาะ
test พวกนี้อยู่ในชุดถาวร เพื่อว่าถ้าวันหลังมีใครทำกฎให้อ่อนลง จะมีอะไรแดงขึ้นมา

**เลือกที่จะปฏิเสธ ดีกว่าให้คำตอบที่ดูน่าเชื่อ**
ใช้กับการตรวจ licence (ปฏิเสธตัวที่ไม่ระบุ), staleness gate (ปฏิเสธข้อมูลเก่า),
evaluation gate (ปฏิเสธโมเดลที่เสมอกับ persistence) และ registry (ปฏิเสธ lineage ที่ไม่ครบ)

**เอาสิ่งที่เรียนจาก lab มาใช้ต่อ แทนที่จะไปค้นพบใหม่**
6 จาก 12 ขั้นตอนข้างบนอ้างอิงสิ่งที่วัดจริงใน Lab 1 ถึง 5
มันไม่ใช่ของประดับ แต่เป็นเหตุผลว่าทำไมการออกแบบนี้ถึงต่างจากแบบที่นึกออกง่าย ๆ
